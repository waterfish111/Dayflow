## 二、90 秒讲述稿

> 我做的是一个日程工具。起因是我自己排计划很烦：想加一件事，要先想哪天、几点、会不会冲突，输入成本比事情本身还高。
>
> 但市面上的 AI 日程工具有个共同问题——让模型直接决定时间。模型不知道你今天 19 点已经排了课，也不知道你每天最多安排 6 小时，它给出的时间是「看起来合理」而不是「真的可行」。
>
> 所以我把这件事拆成两段：**模型只负责把「周三下午组会改到四点，周五前交报告」翻译成结构化字段**，剩下的时间计算交给一个纯函数排期引擎。引擎按优先级、截止时间、每日上限、任务间缓冲去找空档，找不到就退回待办池并说明原因。模型输出永远是草案，用户勾选后才写入日历。
>
> 这样拆的好处是：排期逻辑可以写单测，我用 37 个用例覆盖了冲突避让、截止截断、每日上限、指定日期放不下时的降级这些边界；而模型那部分的不确定性被限制在「解析」这一层，出错最多是多一条待确认的草案，不会污染已有日程。
>
> 工程上是 React + TypeScript + Vite，AI 调用走一个服务端代理（拼 prompt、50 秒超时、错误映射、二次结构校验），部署在 Vercel，PWA 可以装到手机桌面。CI 跑 typecheck、单测和构建。
>
> 这个项目让我体会最深的是「边界」：哪些交给模型、哪些交给代码、哪些交给用户确认。我现在正在补的是账号与多端同步，以及一套固定用例的解析评测。

## 三、预判问题与答法

**Q1：为什么不让 LLM 直接输出时间？**
三个原因：① 它不知道你的日历现状，只能编一个「合理」的时间；② 输出不可复现，同样的输入两次结果可能不同；③ 排期规则（每日上限、缓冲、截止）是业务约束，写在 prompt 里既不可测也不可靠。把「理解语言」和「计算时间」分开后，后者是纯函数，可单测、可回归。

**Q2：排期算法是什么？复杂度？为什么不用更优的解法？**
贪心 first-fit：任务按 优先级 → 截止时间 → 创建时间 排序，每个任务在自己允许的日期范围内逐日、按粒度步进找第一个放得下的空档。复杂度 O(任务数 × 候选天数 × 每天步数)，几十个任务是毫秒级。
不用背包/ILP 的原因：这是个带用户偏好的满意度问题，不是单一目标优化；贪心的结果可解释（「它排在 21:00 是因为 19:00–20:30 被占、20:35 起第一个整点半空档」），而最优解反而难向用户解释。代价是局部最优，比如大任务可能被挤到很晚——这是已知取舍，写在 README 的「已知限制」里。

**Q3：你说有 37 个测试，测的是什么？**
`src/lib/scheduler.test.ts` 22 个：空日历落到作息块起点、有占用时跳过并留缓冲、每日上限用满后顺延到次日、截止当天截断、首选时间向上取整到粒度、指定日期放不下时保留日期但清空时间并返回 warning、只重排选中任务时其他任务不动、事件占时间但不占每日额度、高优先级先占位、重复规则展开（每日 / 每周指定星期 / 间隔天数 / until 截止）。
`src/lib/date.test.ts` 15 个：墙上时间与分钟数互转、跨零点免打扰、周一为首日的周界、日期加减。
CI 里 `pnpm test` 是真跑 vitest，不是 mock。

**Q4：AI 输出不可靠，你怎么兜？**
四层：① 请求侧 `response_format: json_object` + `temperature 0.1`；② 服务端 `normalizeAiResult` 校验字段类型、枚举、时间格式，非法就丢弃该条；③ 客户端 `sanitizeItem` 再用正则校验 `HH:mm` / `YYYY-MM-DD`，防止绕过服务端；④ 产品层：每条草案带 confidence，低于 0.7 默认不勾选，信息不足时模型返回 questions 让用户补充。失败路径有明确文案（Key 无效 / 太频繁 / 超时 / JSON 解析失败）。

**Q5：Key 为什么存在 localStorage？安全吗？**
这是个人工具的取舍：没有账号体系，Key 只能存在浏览器里，明文存 localStorage。为此加了一个服务端代理，作用是拼 prompt、统一超时与错误、做二次校验，顺便避免浏览器直连 DeepSeek 的 CORS 问题。
真正的风险点我排查过：代理在没有请求头 Key 时会回退到 `DEEPSEEK_API_KEY` 环境变量，如果部署方配了它，任何人都能免 Key 调用。我验证过线上生产环境没有配这个变量（不带 Key 请求返回 400「还没有配置 Key」），README 里也写了警告。要做成公开产品，正确做法是服务端持有 Key + 登录态 + 按用户限流。

**Q6：42 天这个数字怎么来的？为什么是 +1？**
重复任务展开的默认窗口是 42 天（6 周，够覆盖一个多月）。写测试时发现 `horizonDays=5` 会返回 6 条——因为循环把起始日算了一次、`addDaysKey(date, horizon)` 又把终点算了一次，是闭区间双计。这个 off-by-one 我没改（改它会让已有用户的历史重复任务突然少一天），而是在 README 的「已知限制」里写明，并让测试把这个行为固定下来，避免以后无意改动。

**Q7：如果用户有 500 个任务？**
现在会明显变慢：每个任务都要遍历候选日期和每天的步进点。可行的优化是先把每天的已占用区间建成有序数组、用二分找空档，把单任务的搜索从「逐格试探」变成「按区间跳跃」；再往上就是把排期放到 Web Worker，避免阻塞输入。目前没做，因为个人场景下任务量在几十的量级。

**Q8：时区和跨天怎么处理的？**
全程用「墙上时间」字符串（`YYYY-MM-DD` + `HH:mm`），不构造带时区的 `Date` 再取本地字段——那样会掉进 UTC 偏移的坑（比如 UTC+8 的凌晨会变成前一天）。跨零点的免打扰（23:00–07:00）单独判断。代价是不支持跨时区旅行场景，这是我明确不做的事。

**Q9：部署踩过什么坑？**
两个。① Vercel 首次构建失败，报 `ERR_PNPM_IGNORED_BUILDS`，根因是 `pnpm-workspace.yaml` 里 `allowBuilds.esbuild` 留了占位值，pnpm 11 直接拒绝构建，改成 `true` 后通过。② 部署成功了，但手机打不开——本机走代理能访问 `vercel.app`，手机没有代理。这让我意识到「部署成功」和「用户可达」是两件事，现在正打算绑自定义域名。

**Q10：为什么不用 LangChain / 现成的日程库？**
这个项目里 AI 的部分只有「一次 JSON 模式的补全调用 + 一层结构校验」，引入框架会增加抽象和体积，收益接近零。排期部分没有找到语义匹配的库（大多数是日历 UI 或 RRULE 解析），而排期恰好是我想自己写、也最值得写测试的部分。

**Q11：重复任务改一次会影响整组吗？**
不会，这是已知限制：展开后的每次是独立条目，改一次只改那一次。正确做法是存 RRULE 规则、渲染时展开，改单次存 exception。没做的原因是改动会波及数据模型和拖拽逻辑，我把它排在云同步之后。

**Q12：无障碍做到了什么程度？**
按钮都有 `aria-label`，弹窗支持 Esc 关闭、打开时锁滚动、尊重 `prefers-reduced-motion`。没做的是焦点陷阱和关闭后的焦点归还，这是下一步要补的（Modal 组件只有 100 行，加 focus trap 成本很低）。

## 四、现场可以演示的三个动作

1. 输入「明天下午三点跟产品经理开需求评审会，晚上写两小时周报；周五前把季度复盘文档写完」→ 展示 4 条草案：一条事件、两条任务、一条低置信度默认不勾选
2. 点「确认并写入日历」→ 周视图里自动落到空档，右侧待办池数量变化
3. 打开 `src/lib/scheduler.ts` 的 `findSlotOnDate`，现场讲 30 秒「它怎么判断这个位置能不能放」

## 五、诚实边界（被问到时不要绕）

| 没做的 | 现状 | 计划 |
|---|---|---|
| 账号 / 多端同步 | 只有 localStorage，能导出不能导入 | Supabase Auth + Postgres + RLS，repository 层替换 |
| 后台提醒 | 只在页面打开时每 30 秒轮询 | Web Push 或 Capacitor 本地通知 |
| 解析准确率 | 没有量化 | 20 条固定中文用例 + 字段级打分脚本 |
| 国内访问 | 直连 `vercel.app` 不稳定 | 自定义域名或国内托管 |
| 代码结构 | `App.tsx` 712 行，业务逻辑集中 | 拆成 hooks + reducer |

## 六、一句话总结（面试收尾用）

> 这个项目技术上最难的不是调模型，是「承认模型不可靠」，然后围绕这个事实设计边界：它能做什么、它的输出要经过几道校验、哪些决定必须留给用户。
