# Dayflow 学习笔记

这份笔记配合项目代码阅读，重点不是“用了什么框架”，而是理解一个日程产品为什么这样拆分。

## 1. 整体数据流

```text
用户输入一句话
      │
      ▼
POST /api/ai/parse
      │  服务端代理，不把 Key 写进前端
      ▼
DeepSeek 返回 JSON
      │  只描述“有哪些事、什么时候、多久”
      ▼
计划草案（DraftItem）
      │  你勾选、补充、确认
      ▼
排期引擎 autoSchedule()
      │  根据作息、空闲时段、优先级、截止时间找位置
      ▼
正式日程（ScheduleItem）
      │
      ├── 周 / 日 / 月视图
      ├── 提醒检查
      └── localStorage 持久化
```

关键原则：**AI 负责理解语言，程序负责计算时间**。

让大模型直接输出“周三 14:00–16:00 开会”可以，但不要让它负责“今天还剩多少空档、两个任务会不会重叠、每天最多几小时”。这些是确定性的约束，交给代码更稳定、可测试、也更容易解释。

## 2. React 状态是怎么流动的

入口在 `src/App.tsx`：

- `state` 保存任务和设置，初始值从 `loadState()` 读取。
- 每次 `state` 变化，`useEffect` 调用 `saveState()` 写回 `localStorage`。
- `scheduledTasks` 和 `poolTasks` 都是派生数据，不单独存储：

```ts
const scheduledTasks = state.tasks.filter(isTaskScheduled);
const poolTasks = state.tasks.filter((task) => !isTaskScheduled(task));
```

这体现了一个重要习惯：**能推导出来的数据不要重复存**。任务有没有日期和时间，已经足够判断它在日历里还是在待办池里。

`TaskEditor` 使用受控表单：输入框的值来自 React state，`onChange` 更新 state。这样做的好处是保存时可以统一校验，缺点是日期/时间控件在不同浏览器里的输入事件行为不完全一致，测试时要使用真实交互或原生事件。

## 3. 日期和时间为什么单独抽一层

`src/lib/date.ts` 里统一处理：

- `YYYY-MM-DD` 日期键
- 本地时区下的 `Date`
- 周一开始的一周
- 月份网格
- `HH:mm` 与分钟数互转
- 免打扰的跨午夜判断

日程产品最容易出错的地方之一，是把“日期字符串”和“时间戳”混着用。这里的约定是：

- 日期用 `YYYY-MM-DD`，表示用户看到的那一天。
- 时间用 `HH:mm`，表示当天的墙上时间。
- 截止时间用 `YYYY-MM-DDTHH:mm`。
- 需要比较先后时，再转成 `Date` 或分钟数。

这样不会因为 UTC 换算，把“晚上 11 点的任务”显示到第二天。

## 4. 排期算法在做什么

核心在 `src/lib/scheduler.ts` 的 `autoSchedule()`。

它把每个任务看成一段有长度的时间，把日历看成若干“可用窗口”和“已占用区间”：

```text
工作日可用窗口：19:00–22:00
已占用：19:00–20:30 写报告
新任务：60 分钟
结果：20:35 之后找空档，按 30 分钟粒度落到 21:00–22:00
```

排期时依次考虑：

1. 任务优先级：高 → 中 → 低。
2. 截止时间：越早越优先。
3. 任务时长和当天剩余上限。
4. 固定日程、已排任务、锁定任务的占用。
5. 任务间缓冲，默认 5 分钟。
6. 首选时间；如果冲突，就在同一天继续找。
7. 当天放不下，就尝试下一天，最多看 21 天。

几个重要概念：

- **硬约束**：固定会议、锁定任务、截止时间、每日上限。违反就不能排。
- **软约束**：优先级、首选时间、尽早安排。尽量满足，但可以退让。
- **确定性**：同样的输入应该得到同样的结果。算法不应该依赖随机数或模型发挥。

如果任务找不到空档，`autoSchedule()` 不会偷偷把它塞到不合适的时间，而是返回 warning，让任务留在待办池。这是“可解释”的一部分。

## 5. AI 层如何设计

`server/index.mjs` 负责：

1. 从请求头读取当前使用者自己的 `x-deepseek-key`。
2. 把当前日期、时区、分类、作息模板和用户输入拼成提示词。
3. 要求模型只输出 JSON。
4. 解析 JSON，清洗字段，返回给前端。

提示词里明确要求：

- 一句话里有几件事，就输出几个 items。
- 不把一个任务拆成多个步骤（当前版本取消了大任务拆分）。
- 日期按“当前日期”换算。
- 信息不够时在 `questions` 里反问，不要编造。
- 每个 item 给 `confidence`，前端据此决定是否默认勾选。

前端 `src/lib/ai.ts` 还会再清洗一次日期、时间和优先级，避免模型返回意外格式。

**为什么要服务端代理？**

如果把 DeepSeek Key 写在 React 代码里，任何人打开网页都能在构建产物里看到。代理层让 Key 只在请求处理期间出现在服务端内存中；当前版本不把 Key 写入数据库。

**为什么还要人工确认？**

模型可能把“周日截止”理解成“周日开始”，也可能漏掉时长。混合确认的流程是：

- 高置信度条目默认勾选。
- 低置信度条目标为“需确认”，默认不勾选。
- 有疑问时先展示问题，允许补充说明后重新解析。
- 只有你点击“确认并写入日历”才落正式数据。

## 6. 优先级、锁定和完成

- 优先级只负责视觉和排序：红点高、黄点中、绿点低。
- 未完成用独立的红色角标/边框表达，避免和优先级红点混淆。
- `locked` 是排期算法的硬约束。拖拽和自动排期都会先检查它。
- 完成状态只影响显示和提醒；当前版本不做统计报表。

## 7. PWA 和通知

`public/manifest.webmanifest` 让 Android Chrome 可以把网页安装到主屏；`public/sw.js` 是 service worker，负责缓存页面资源，让断网时至少能打开已缓存的界面。

通知的现实限制：

- 浏览器通知需要安全上下文，`localhost` 例外；手机通过局域网 HTTP 打开时，通常不能授权通知。
- 网页关闭后，JavaScript 定时器不会可靠运行。`checkReminders()` 目前只在应用打开时每 30 秒检查一次。
- 真正“每天 8 点即使没打开 App 也提醒”，需要 Web Push（服务端保存订阅并定时推送）或封装成手机 App 后使用本地通知。
- iPhone 的网页通知限制更多，Android 优先是合理的第一版选择。

## 8. 离线与数据

当前版本是 local-first：

- 任务、设置、通知发送记录都在 `localStorage`。
- 断网时仍然可以查看、添加、修改、完成和触发已安排任务的本地通知。
- AI 依赖网络，断网时会提示不可用。
- 换浏览器、清缓存或换手机不会自动同步。

迁移到 Supabase 时，建议保留当前的数据模型，把 `ScheduleItem[]` 和 `Settings` 映射到两张表：

- `tasks`：每个任务一行，包含 `user_id`、日期、时间、优先级、锁定、完成等字段。
- `settings`：每个用户一行，作息模板和分类用 `jsonb` 保存。

前端把 `loadState/saveState` 换成 repository 层，组件不需要重写。再用 Supabase Auth 的邮箱密码登录和 Row Level Security 保证每个账号只能读写自己的数据。

## 9. 建议的练习

1. 修改 `DEFAULT_SETTINGS.workday.maxMinutes`，观察自动排期什么时候开始拒绝任务。
2. 把 `bufferMinutes` 改成 30，观察任务之间的空档变化。
3. 给 `autoSchedule()` 写一个纯函数测试：固定输入、固定今天日期，断言输出时间。
4. 把 `localStorage` 替换成一个 `StorageAdapter` 接口，再实现 Supabase 版本。
5. 把 `checkReminders()` 拆成“生成提醒事件”和“发送通知”两层，方便测试。
6. 为 `DraftReview` 增加逐条编辑，理解“草案”和“正式数据”的边界。

## 10. 下一阶段建议顺序

1. Supabase Auth + 数据同步（跨设备、换机不丢数据）。
2. Web Push 或 Capacitor 本地通知（真正后台提醒）。
3. 手机 App 封装（Android 优先）。
4. iOS、分享、统计、系统日历同步。

先把“解析—确认—排期—提醒”这条主链路做稳，再增加外围功能，项目会更容易维护。
